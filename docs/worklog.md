PR 번호는 `GadongGadonghae/Back-End` 기준이에요(프론트는 `Front-end #n`).

## 2026-11-18

### 10. DB v0.3.9: 설비별 들어간·나간 시각 추가 → 백엔드 반영 대기
- **배경:** 재공·처리 중·대기·단별 CT를 정확히 보려면 제품이 설비에 언제 들어가고 나갔는지가 필요했어요(9번, 6번에서 이어짐).
- **DB 변경(v0.3.9):**
  - `slitting/welding/painting_data`에 `started_at`·`ended_at`이 생겼어요.
  - `press_data`에 `pr1_started_at` ~ `pr4_ended_at`이 생겼어요.
  - `inspection_result`에 `started_at`이 생겼어요.
  - 행은 **들어갈 때** 생기고, 값과 `ended_at`은 나갈 때 채워져요. `measured_at`은 처음 들어간 시각으로 고정이에요.
- **백엔드가 바꿀 것:**
  - 판정·생산 수는 `ended_at`이 있는 행만 다뤄요. 이걸 안 하면 빈 행을 판정해서 기준치가 없는 슬리팅이 바로 OK가 돼요.
  - 재공은 "앞 설비 `ended_at` 있음 + 다음 설비 `started_at` 없음"으로 세요.
  - I 대기, 사이클·CT도 이 컬럼으로 계산해요.
- **확인할 것:** 실제 DB 적용 시점과 시뮬레이터 전환 시점을 맞춰야 해요. `alter_v0.3.9.sql`이 저장소에 없어요. 씨드와 스키마의 버전 표기, 라인 박자(16초/18초)가 서로 달라요.

### 9. 설비 상태 판정 D > DC > S > I > R 구현 (PR #17)
- **증상:** 상태가 늘 R(가동)이었어요. 판정 PR #11의 상태 판정이 "전부 R" 임시 규칙이었기 때문이에요.
- **해결:** 판정 설계 3·4절대로 만들었어요.
  - **D 고장:** `equipment_signal.fault = 1`
  - **DC 통신 끊김:** 상태 신호 10초 끊김, 또는 신호 행 없음
  - **S 계획정지:** S-02가 만든 이벤트에 연결
  - **I 대기:** 앞에서 넘어와 처리할 제품이 없음
  - **비가동 이벤트:** I·D일 때 `UP_SHORTAGE`·`UP_BREAKDOWN` 이벤트를 만들고, 상태가 바뀌면 닫아요.
- **트러블:** PR #11은 머지 없이 닫혀 있었어요. 닫힌 PR은 새 커밋을 받지 않아서 같은 브랜치로 #17을 새로 열었어요.
- **트러블:** 테스트에서 계획정지가 S로 안 잡혔어요. `Kst.now()`가 초 단위로 잘려서, 같은 초에 넣은 행이 "아직 안 시작"으로 보였어요. S-02도 초 단위로 저장해서 운영에는 문제가 없어요. 테스트 시각만 1분 앞으로 바꿨어요.
- **남은 것:**
  - `equipment_signal`을 시나리오가 채워야 해요. 비어 있으면 전부 DC로 보여요.
  - I 대기는 지금 행 수로 계산해요. v0.3.9 컬럼으로 바꿔야 해요.

### 8. 재공이 시작하자마자 1로 보임 (fix/wip-in-process, 미반영)
- **증상:** 시뮬레이션을 시작하자마자 슬리팅→프레스 재공이 라인마다 1로 떴어요.
- **원인:** 프레스 행이 PR1을 끝낼 때 생겨서, PR1에서 처리 중인 제품이 재공으로 세졌어요. 용접 앞도 같았어요.
- **임시 해결:**
  - 프레스·용접 앞 재공에서 라인마다 처리 중 1개를 뺐어요.
  - 라인별로 빼고 합쳐요. 그래야 한 라인이 비어 있어도 다른 라인 재공이 줄지 않아요.
- **추가 증상:** B라인 재공이 4에서 갑자기 1로 떨어졌어요.
  - 데이터를 보니 프레스 행 3개가 3초 안에 생겼어요. 계산은 맞고, 시뮬레이터가 한꺼번에 넣은 것으로 보여요.
  - 다만 당시 DB에는 행이 처음 생긴 시각이 남지 않아서 확정하지 못했어요. → 10번 컬럼으로 확인할 수 있어요.
- **정리:** 재공(슬리팅→프레스) = 슬리팅 OK 수 − PR1을 거친 프레스 행 수예요. PR4와 비교하는 게 아니에요.
- **남은 것:**
  - 도장·검사는 공용 설비라서 처리 중 1개가 어느 라인 제품인지 몰라 보정하지 않았어요.
  - v0.3.9 컬럼이 들어오면 이 추정은 지우고 시각 컬럼으로 바꿔요.

### 7. 백엔드가 안 뜸: `Unable to determine Dialect`
- **원인:** `application-local.yml`의 DB 주소 포트를 `5173`(프론트 개발 서버 포트)으로 잘못 적었어요.
- **해결:** `jdbc:postgresql://192.168.0.13:5432/sfaas`로 바꿨어요.
- **참고:** `application-local.yml.example`에 `url`·`username` 줄이 없어요. 빼먹으면 `localhost`로 접속해서 같은 오류가 나요.

### 6. 로그인은 되는데 API가 401
- **원인:** 오늘 `jwt.secret`을 바꿔서, 예전 비밀키로 만든 토큰이 거부됐어요.
- **해결:** 다시 로그인하면 돼요. 백엔드마다 `jwt.secret`이 다르면 다른 백엔드로 옮길 때마다 다시 로그인해야 해요.

### 5. DB 컴퓨터와 내 화면이 다르게 보임
- **원인:** 백엔드 두 대가 같은 DB를 보고 있었어요. 화면은 각자 붙은 백엔드의 판정 결과를 보여 줘요.
- **해결:** 프론트 `.env.local`의 `BACKEND_URL`로 붙을 백엔드를 고르면 돼요.
- **규칙:** **판정이 들어간 백엔드는 한 대만 켜요.** 여러 대가 같은 DB에 판정을 쓰면 결과와 상태 이력이 겹쳐요.
- **참고:** 백엔드는 `docs/`를 읽지 않아요. 데이터는 DB에서 바로 읽어요.

## 2026-11-17

### 4. 평균 사이클타임이 이상함, 프레스 설정 17초와 다름 (PR #16)
- **원인:**
  - 프레스 행의 `measured_at`이 단을 지날 때마다 덮여서, PR1 시각인 줄 알고 계산한 CT가 틀렸어요.
  - 평균은 시작·정지 구간의 긴 간격에 끌려갔어요.
- **해결:**
  - CT를 같은 설비 행 간격의 **중앙값**으로 바꿨어요.
  - 프레스는 PR4만 CT를 내요.
- **배경:** 실측 평균은 슬리팅 약 16.3초, 프레스 약 19초였어요. 시뮬레이터 프레스 CT가 17초 근처에서 무작위로 흔들리고 단끼리 맞물려 기다려서, 슬리팅→프레스 재공이 계속 쌓였어요.
- **남은 것:** 단별 CT는 단별 시각이 필요해서 DB에 요청했어요. → 10번

### 3. 오늘 사이클·시간대별 그래프·도장 재공이 안 보임 (PR #14·#16, Front-end #1)
- **해결:**
  - M-15 사이클을 추가했어요.
  - 시간대별은 별도 API를 만들지 않고 G-01 `unit=hour`로 통일했어요. 처음 만든 M-14는 중복이라 지웠어요.
  - 프레스 그래프를 단별로 고쳤어요.
  - M-13에 `paintId`를 넣어 도장 설비별 앞뒤 재공을 볼 수 있게 했어요.
  - 제품 추적 API를 추가했어요: `/api/products`, `/api/products/{id}`, `/api/production/process-ng`.

### 2. 프론트에서 "요청값이 올바르지 않음"(400), 로그인 페이지로 튕김(401)
- **원인:** 프론트 어댑터가 명세와 다르게 보냈어요.
  - 기간을 시각까지 붙여서 보냈어요.
  - `size`가 100을 넘었어요.
  - 401 처리가 없었어요.
- **해결(Front-end #1):** 날짜만(`YYYY-MM-DD`) 보내고, `size`는 100 이하로 맞췄어요. 401이면 로그인 화면으로 보내요.
- **참고:** 페이지 응답은 `{items,total,page,size}`이고 `page`는 1부터예요. 명세의 0부터와 다르지만 일부러 유지해요.

### 1. 로그인 후 데이터가 전부 비어 있음
- **원인:** 판정이 돌지 않아서 `result`와 설비 상태가 전부 비어 있었어요. 재공, 양품률, 상태가 모두 판정 결과로 계산돼요.
- **해결:** 판정(`feature/judge-skeleton`)을 합친 실행용 로컬 브랜치 `local/run-all`로 돌렸어요.
